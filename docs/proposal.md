# 智能健身与营养追踪系统 · 项目提案

Oct 23, 2026 · @Stan

## 1. 项目概述

本项目构建一个个人健身数据中枢：把身体数据标准化存入数据库，由 AI agent 据此生成结构化的训练与饮食计划，并按执行反馈持续微调。

**要解决的问题**：身体数据分散在体重秤、手表和笔记里；训练计划要么一成不变，要么随意更改、失去周期结构；饮食记录与训练目标脱节。

**项目目标**

- 统一数据：所有身体指标、训练记录、饮食记录以统一 schema 入库，可查询、可追溯
- 结构化计划：输出日 / 周 / 月 / 年四级标准格式的训练计划
- 闭环调整：根据进度数据自动微调负荷与热量，但不破坏周期化结构
- 热量管理：自动计算 BMR / TDEE 与宏量营养素目标，追踪每日摄入

## 2. 核心功能

系统由四个功能模块组成，彼此通过数据库共享状态。

| 模块 | 输入 | 输出 | 频率 |
| --- | --- | --- | --- |
| 身体数据录入 | 身高、年龄、性别、体重、体脂率、围度、静息心率 | 校验后的标准记录；趋势（7 日均值） | 每日 / 每周 |
| 训练计划生成 | 目标、训练经验、可用天数与器械、伤病史 | 年度周期 → 月度阶段 → 周模板 → 日课表 | 初始化 + 每周 |
| 训练执行记录 | 实际完成的组数、次数、重量、RPE | 完成率、训练量、e1RM 变化 | 每次训练 |
| 营养与热量追踪 | 食物与份量、或宏量营养素 | 当日摄入 vs 目标；热量平衡 | 每日 |

**交互方式**：初期以对话 / 命令行录入（如 "体重 72.4 体脂 18.5"），agent 解析为结构化数据后写库；后期可接入体脂秤、运动手表的数据导出。

## 3. 系统架构

系统分为交互层、Agent 层、计算层和数据层，形成"录入 → 计划 → 执行 → 回流 → 微调"的闭环。

Agent 不直接计算数值，也不绕过规则引擎写库；这是计划保持严格结构的关键。

## 4. 数据模型

所有数据采用公制单位、ISO 8601 日期，每条记录带 `source`（手动 / 设备 / agent）与时间戳，保证可追溯。核心表如下：

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `user_profile` | 身高 cm、出生日期、性别、训练经验、目标、伤病史 | 低频变动的静态信息 |
| `body_metrics` | 日期、体重 kg、体脂 %、去脂体重 kg、围度 cm、静息心率 | 时间序列，去脂体重自动计算 |
| `exercise_library` | 动作名、主要肌群、动作模式、器械 | 标准动作字典，避免同名异写 |
| `program` | 周期 ID、层级（年/月/周）、阶段类型、起止日期、目标 | 树状结构：年 → 中周期 → 微周期 |
| `planned_session` | 日期、所属微周期、动作、组 × 次、目标强度（%1RM 或 RPE） | 计划值 |
| `workout_log` | 关联 planned\_session、实际组数 / 次数 / 重量 / RPE | 实际值，与计划一一对应 |
| `nutrition_target` | 生效日期、热量 kcal、蛋白 / 碳水 / 脂肪 g | 每次调整生成新版本 |
| `food_log` | 日期、餐次、食物、份量 g、kcal、宏量营养素 | 每日摄入 |
| `adjustment_log` | 日期、触发原因、改动内容、前后值 | 记录 agent 每次微调，可回滚 |

**设计原则**：计划值与实际值分表存储，便于计算完成率与偏差；所有 agent 修改写入 `adjustment_log`，而非直接覆盖历史。

## 5. 训练计划结构

计划采用经典周期化（Periodization）四级结构，上层锁定方向，下层承接执行；层级越高越稳定，越低越灵活。

| 层级 | 时长 | 定义内容 | 可调整范围 |
| --- | --- | --- | --- |
| 年度大周期 Macrocycle | 12 个月 | 年度目标、阶段顺序（如增肌 → 力量 → 减脂 → 维持） | 仅在季度复盘时调整 |
| 中周期 Mesocycle | 4–6 周 | 阶段类型、训练量与强度区间、热量策略（盈余 / 维持 / 缺口） | 阶段末评估，可延长或提前切换 |
| 微周期 Microcycle | 1 周 | 训练分化（如上下肢 / PPL）、每日主题、每肌群周组数 | 每周微调组数与重量 |
| 训练日 Session | 1 天 | 动作、顺序、组 × 次、强度（%1RM / RPE）、休息时间 | 当日可按状态小幅调整 |

每个中周期末尾内置一周减载（Deload）。

**日课表标准格式**（示例）

```markdown
日期：2026-11-02 | 中周期：增肌 M1 · 第 2 周 | 主题：上肢推
1. 杠铃卧推      4 × 6–8   RPE 8   休息 180s
2. 上斜哑铃卧推  3 × 8–10  RPE 8   休息 120s
3. 站姿推举      3 × 8–10  RPE 7–8 休息 120s
4. 绳索侧平举    3 × 12–15 RPE 9   休息 60s
备注：卧推上周 4×8 @ 80kg 全部完成 → 本周 82.5kg
```

## 6. 营养与热量计算

热量目标由公式给出初始值，再用实际体重趋势反推真实消耗并校准。

**第一步：基础代谢 BMR**。有体脂数据时优先用 Katch-McArdle，否则用 Mifflin-St Jeor：

```latex
BMR_{Katch} = 370 + 21.6 \times LBM_{kg}
```

```latex
BMR_{Mifflin} = 10W + 6.25H - 5A + s \quad (s = +5\ \text{男},\ -161\ \text{女})
```

**第二步：总消耗 TDEE** = BMR × 活动系数（1.2–1.9，按日常活动与训练频率选择）。

**第三步：按阶段设定目标**

| 阶段 | 热量 | 蛋白质 | 脂肪 | 碳水 |
| --- | --- | --- | --- | --- |
| 增肌 | TDEE + 5–10% | 1.6–2.2 g/kg | 0.8–1.0 g/kg | 剩余热量 |
| 减脂 | TDEE − 15–25% | 2.0–2.4 g/kg | 0.6–0.8 g/kg | 剩余热量 |
| 维持 | TDEE | 1.6–2.0 g/kg | 0.8–1.0 g/kg | 剩余热量 |

**第四步：自适应校准**。每 2 周比较平均摄入与体重变化（约 7,700 kcal ≈ 1 kg 体重），反推实际 TDEE，替换公式估算值。体重以 7 日移动平均为准，过滤水分波动。

## 7. 微调机制与结构约束

"灵活微调"与"严格结构"靠规则分层实现：agent 只能在规则引擎允许的范围内修改下层参数，不能改写上层结构。

**调整规则（示例）**

| 触发条件 | 调整动作 | 作用层级 |
| --- | --- | --- |
| 某动作连续 2 次完成全部组次且 RPE ≤ 目标 | 重量 +2.5 kg（上肢）/ +5 kg（下肢） | 训练日 |
| 某动作连续 2 次未完成目标次数 | 重量 −5%，或保持并降低组数 | 训练日 |
| 周平均 RPE 偏高 1 以上，或睡眠 / 疲劳评分差 | 下周组数 −20% 或提前减载 | 微周期 |
| 减脂期 2 周体重下降 < 0.25% / 周 | 热量 −100 至 −150 kcal | 营养目标 |
| 减脂期体重下降 > 1% / 周 | 热量 +100 kcal，防止肌肉流失 | 营养目标 |
| 中周期结束，目标达成或停滞 | 进入下一阶段 / 延长 1–2 周 | 中周期 |

**结构约束（不可被 agent 越过）**

- 每次调整幅度设上限：重量单次 ≤ 5%，热量单次 ≤ 150 kcal，周组数单次 ≤ 20%
- 年度阶段顺序与中周期类型只在复盘节点、经用户确认后变更
- 每周训练日数、训练分化在一个中周期内保持不变
- 所有输出须通过 schema 校验（JSON Schema / Pydantic），不合格则重试或回退
- 每次调整写入 `adjustment_log` 并附理由，可一键回滚

## 8. 技术选型与实施路线

建议从单用户、本地优先的轻量栈起步，验证闭环后再扩展界面与设备接入。

| 层 | 推荐方案 | 理由 |
| --- | --- | --- |
| 数据库 | PostgreSQL | 零运维起步，schema 可平滑迁移 |
| 后端 / 逻辑 | Python + Pydantic + SQLAlchemy | 数据校验与 ORM 成熟 |
| 计算与规则引擎 | 纯 Python 模块（公式、进阶规则、约束检查） | 确定性计算不交给 LLM |
| Agent | 免费模型优先 其次api + 工具调用（读写数据库、调用规则引擎） | 负责解析输入、生成计划、解释调整理由 |
| 交互界面 | 先命令行 / 对话 → 后续 Web 仪表盘 | 先验证功能再投入 UI |
| 食物数据 | USDA FoodData Central | 标准化营养数据来源 |

**关键分工**：所有数值计算（BMR、TDEE、重量递增、热量调整）由确定性代码完成；LLM 负责理解自然语言、编排计划内容和解释原因。这样既保证结果可复现，也让结构不会被"自由发挥"打乱。

每个阶段达到门槛后再进入下一阶段；阶段 3 完成即具备完整的"记录 → 计划 → 微调"闭环。

## 9. 风险、边界与成功指标

**主要风险与应对**

| 风险 | 应对 |
| --- | --- |
| 体脂秤（BIA）误差大，单日波动 2–3% | 只用趋势值；同一设备、同一时段测量 |
| 饮食记录不完整，导致 TDEE 校准失真 | 记录完整度 < 80% 的周不参与校准 |
| LLM 输出格式漂移或数值幻觉 | 数值由代码计算；输出强制 schema 校验 |
| 过度调整，计划失去连续性 | 调整幅度上限 + 层级锁定（第 7 节） |

**边界**：本系统提供训练与营养建议，不替代医疗诊断。有伤病、慢性病或特殊饮食需求时，应先咨询医生或注册营养师。

**成功指标**

- 数据：连续 8 周体重与训练记录完整度 ≥ 90%
- 计划：计划完成率 ≥ 85%，结构违规调整 0 次
- 结果：主项 e1RM 每个中周期提升，或体重变化落在目标区间内
- 体验：每日录入耗时 < 2 分钟
